### スライド 3：ABテストとは何か——統計的仮説検定とFisher（1935）の実験設計（1:20〜2:10）

**スライド内容：**
```
【見出し】ABテストとは何か——実験で「原因」を特定する手法

【定義】
　ABテスト（A/Bテスト）とは、
　「同じ条件下で1つの変数だけを変えた2つのバージョンを
　 ランダムに振り分けて比較し、どちらが優れているかを
　 統計的に判断する手法」

【コントロール群とテスト群】
　A（コントロール群）：現在のバージョン（変えない）
　B（テスト群）    ：改善案のバージョン（1か所だけ変える）
　→ 2つを同時に、ランダムに見せて、結果を比較する

【起源：Ronald A. Fisher（1935）】
　農業実験で確立した「実験計画法」の原則
　『The Design of Experiments』
　① ランダム化（Randomization）：偶然の偏りを排除する
　② 反復（Replication）：十分なサンプル数で信頼性を高める
　③ 局所管理（Local Control）：比較条件を揃える

【ABテストはこの原則をウェブに応用したもの】
```

**アニメーション：** 定義テキストがフェードイン → A・B群が左右に分かれて矢印で対比表示 → Fisher（1935）の3原則がビルドアップ

**ナレーション：**
「ABテストとは、1つの変数だけを変えた2つのバージョンを、ランダムに振り分けて比較し、統計的に判断する手法です。
この考え方の基礎は1935年、イギリスの統計学者ロナルド・フィッシャーが農業実験のために確立した「実験計画法」にあります。肥料を変えると収穫量が上がるか——これを正しく測るための3原則、ランダム化・反復・局所管理がABテストの骨格です。90年前の農業科学が、現代のウェブマーケティングに直結しているんですね。」

### スライド 5：サンプルサイズと検出力——「5人が良いと言った」では信頼できない理由（3:00〜3:50）

**スライド内容：**
```
【見出し】サンプルサイズ——「何人のデータが必要か」を事前に決める

【なぜサンプルサイズが重要か】
　「5人に見せて4人が良いと言った」
　→ コインを5回投げて4回表が出ても「このコインは表が出やすい」とは言えない
　→ 少ないサンプルでは、偶然の差を「効果あり」と誤判断してしまう

【統計的有意差（p値）とは】
　p値 < 0.05 = 「この差が偶然起きる確率が5%以下」
　→ 「95%の確率で、Bの方が本当に良い」という目安
　※「5%以下の確率で偶然」＝「95%の確率で本物の差」と考える

【必要サンプルサイズの目安（CVRテストの場合）】
　現在のCVR        最低必要サンプル数（片側）
　──────────────────────────────────────────
　1%（100人に1人）  約4,000〜8,000 セッション
　3%（100人に3人）  約1,500〜3,000 セッション
　5%（100人に5人）  約800〜1,500 セッション

　→ 検出したい改善幅が小さいほど、必要サンプルは増える
　→ 事前計算ツール：Evan Miller の Sample Size Calculator などを活用

【結論】
　テスト開始前に「いくつのサンプルが必要か」を必ず計算する
```

**アニメーション：** コインのたとえが視覚化（コイン×5のアニメーション）→ p値の説明がシンプルな図で出現 → サンプルサイズ表が1行ずつビルドアップ → 結論が強調表示

**ナレーション：**
「「5人に見せて4人が良いと言った」——これはデータとして信頼できません。コインを5回投げて4回表が出ても、そのコインが偏っているとは言えないのと同じです。少ないサンプルでは偶然の差を「効果あり」と誤判断してしまいます。
統計的有意差を示す指標がp値です。p値が0.05未満なら「この差が偶然起きる確率は5%以下」、つまり95%の確率で本物の差があると判断できます。現在のCVRが1%なら片側で4,000〜8,000セッション、3%なら1,500〜3,000セッション程度が最低ラインです。テスト開始前に必要サンプル数を計算してください。」

### スライド 6：よくある失敗①——早期終了の罠（Evan Miller 2010）（3:50〜4:40）

**スライド内容：**
```
【見出し】よくある失敗① 早期終了——「途中で良さそうだから終了」は危険

【早期終了とは】
　テストを途中でのぞき見て
　「Bが優勢！もうBで決定しよう」と終了してしまうこと

【何が起きるか：Evan Miller（2010）"How Not To Run An A/B Test"】

　テスト開始直後のサンプル推移イメージ：

　　時間軸 →
　　100人時点：B優勢 → 「Bが勝ちそう！」→ 早期終了
　　500人時点：A・Bほぼ同等
　　1000人時点：実はAの方が優勢だった

　→ 途中でのぞくたびに「誤検知のリスク」が累積する
　→ 5%の有意水準でも、途中チェックを繰り返すと
　   フォールスポジティブ（偽の陽性）率が20〜30%超になる

【フォールスポジティブとは】
　「効果がないのに、効果があると誤判断してしまうこと」

【正しい対処法】
　① テスト開始前に「必要サンプル数」を決める
　② サンプルに達するまで結果を見ない（または見ても判断しない）
　③ 事前に設定した期間が終わってから判断する
```

**アニメーション：** 折れ線グラフが時間軸とともにアニメーション（A・Bの逆転が起きる様子を視覚化）→ 「早期終了」の矢印が100人地点に出現 → フォールスポジティブの解説が出現 → 3つの対処法がビルドアップ

**ナレーション：**
「最も多い失敗が早期終了です。テストを始めて数日後、「Bが優勢に見える、もう決めよう」と終了してしまうパターンです。
2010年にEvan Millerが指摘した問題がまさにこれです。テスト途中でのぞくたびに「誤検知のリスク」が積み重なります。5%の有意水準を設定していても、途中チェックを繰り返すとフォールスポジティブ——本当は効果がないのに「効果あり」と誤判断する確率——が20〜30%を超えることもあります。
対処法はシンプルです。開始前に必要サンプル数を決め、達成するまで判断しない。それだけです。」

### スライド 7：よくある失敗②——複数変数を同時に変える（4:40〜5:30）

**スライド内容：**
```
【見出し】よくある失敗② 複数変数の同時変更——「どれが効いたか」がわからなくなる

【やってしまいがちなこと】
　A（現行）：青いボタン ＋ 現行ヘッドライン ＋ 通常画像
　B（改善案）：赤いボタン ＋ 新しいヘッドライン ＋ 新しい画像

　→ BのCVRがAより高かったとき、何が効いたのか不明
　　・ボタンの色？ ヘッドライン？ 画像？ 組み合わせ？
　→ 改善要因が特定できないため、次の施策に活かせない

【1テスト1変数の原則】
　A：青いボタン ＋ 現行ヘッドライン ＋ 通常画像（変えない）
　B：赤いボタン ＋ 現行ヘッドライン ＋ 通常画像（ボタンだけ変える）
　→ 差異の原因が「ボタンの色」だけになる

【例外：多変数テスト（MVT: Multivariate Test）】
　複数要素を同時に組み合わせてテストする高度な手法
　→ 必要サンプル数が非常に多くなる
　→ 月間10万PV以上の規模がない場合はABテストを推奨

【結論】
　初心者は必ず「1テスト1変数」から始める
　「どれが効いたか」がわかってこそ、次の改善に活かせる
```

**アニメーション：** A・Bの複数変化が赤字で強調 → 「？」マークが複数出現 → 1変数版のA・Bが並んで出現 → 結論が強調表示

**ナレーション：**
「2つ目の失敗は、複数の変数を同時に変えてしまうことです。ボタンの色、ヘッドライン、画像を全部変えてBがA比で高かったとき、「何が効いたか」がわかりません。ボタン？ヘッドライン？画像の組み合わせ？この状態では次の施策に知見を活かせません。
ABテストの鉄則は「1テスト1変数」です。変えるのは1か所だけ。そうすることで「これが効いた」という因果関係が明確になります。複数要素を同時にテストするMVTという手法もありますが、月間10万PV以上の規模がないと信頼できる結果が出ません。まずは1変数から始めましょう。」

### スライド 8：よくある失敗③——季節・曜日・時間帯の影響を無視する（5:30〜6:20）

```

【実際に起きやすい問題】
　月曜日だけ3日間テスト → 月曜はビジネス系コンテンツの閲覧が多い日
　→ 土日のレジャー層には全く当てはまらない結果が出る

　→ 1月に同じ施策を打っても同じ結果にはならない

　曜日：　月〜金はBtoBユーザー多め、土日はBtoCユーザー多め

　避ける：祝日をまたぐ・大型セール期間と重ねる

【テスト期間のチェックリスト】
　□ 7日間以上のデータが含まれているか
　□ 特別なイベント・セール・祝日が含まれていないか
　□ 同時並行で別の大きな施策変更をしていないか
```

「3つ目の失敗は、テスト期間が短すぎる、または偏った期間で判断してしまうことです。月曜日だけのデータ、年末商戦中のデータは、ほかの時期に当てはまらない可能性があります。
曜日によってユーザー層が変わる、時間帯で行動パターンが違う、季節で購買意欲が大きく変動する——こうした外部要因の影響を除去するために、テスト期間は最低でも7日間必要です。曜日ごとの偏りを平均化できるからです。理想は2〜4週間。大型セールや祝日をまたぐ期間は避けてください。」

### スライド 10：テスト結果の正しい読み方——CVR・信頼区間・リフト率（7:10〜8:00）

**スライド内容：**
```
【見出し】テスト結果の正しい読み方——3つの指標で判断する

【指標① CVR（Conversion Rate：コンバージョン率）】
　CVR = コンバージョン数 ÷ セッション数 × 100
　例：500セッション中10件購入 → CVR = 2%

　A（現行）：セッション1,000 ／ CV 20件 → CVR 2.0%
　B（改善案）：セッション1,000 ／ CV 24件 → CVR 2.4%

【指標② リフト率（改善率）】
　リフト率 = (B の CVR − A の CVR) ÷ A の CVR × 100
　= (2.4% − 2.0%) ÷ 2.0% × 100 = 20%改善

　→「CVRが0.4%上がった」より「20%改善した」と表現する方が
　　 ビジネスインパクトが伝わりやすい

【指標③ 信頼区間（Confidence Interval）】
　「Bが95%の確率でAより○%〜○%優れている」という範囲
　→ 信頼区間が狭いほど結果の精度が高い
　→ 信頼区間がゼロをまたいでいる場合は「差なし」と判断する

【負のテスト結果から学ぶこと】
　BがAより悪かった場合（失敗のテスト）
　→「このアイデアは効果がない」という重要な知見
　→ 「何がうまくいかなかったか」を仮説として次のテストへ
　→ 失敗は損失ではなく「学習コスト」として捉える
```

**アニメーション：** CVRの計算式がステップ表示 → リフト率の計算が「20%改善」として強調 → 信頼区間が帯グラフで視覚化 → 負の結果の活かし方が最後にフェードイン

**ナレーション：**
「テスト結果の読み方で重要な指標が3つあります。まずCVR——セッション数に対するコンバージョン数の割合です。次にリフト率——CVRがどれだけ改善したかの比率です。2%が2.4%になった場合、上昇幅は0.4ポイントですが、リフト率は「20%改善」と表現します。ビジネスインパクトとして伝わりやすい数字です。
3つ目が信頼区間——結果の精度を示す範囲です。信頼区間がゼロをまたぐ場合は「差なし」と判断します。そしてBがAより悪かった「失敗のテスト」も価値があります。「これは効かない」という知見もまた、次の改善仮説への入口です。」

**スライド内容：**
```
【見出し】今日のまとめ + 「テストして学ぶ」文化を組織に根付かせる

　→ インパクト大 × 変更しやすいものから：ヘッドライン→CTA→価格→画像

　→ ① 早期終了（Evan Miller 2010）——決めた期間・数まで待つ

　→ ③ 短期・偏ったデータ——曜日・季節の影響を除去する

　→ 失敗のテストも「学習」として次の仮説に変える

　・「テストに失敗した」ではなく「仮説を棄却できた」と言い換える
　・Amazonは1日平均10以上のテストを同時進行している（AWS資料）

【今すぐできる実践】
　→ 自社のウェブページで「最初にテストする1か所」を今日決める
　→ 仮説・サンプルサイズ・期間を書き出してテスト計画書を作る
```

- **想定ナレーション文字数：** 約3,200字（10分目安 320字/分×10分）

- **スライド5のサンプルサイズ計算：** Evan Miller の Sample Size Calculator（https://www.evanmiller.org/ab-testing/sample-size.html）を動画概要欄にリンクとして掲載推奨

- **次回との接続：** 実践編が「仮説→検証→改善」のサイクルで締まることを強調し、上級編の「AI + データ」テーマへの橋渡しとして機能させる
